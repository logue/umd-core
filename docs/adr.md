要決定のテストは、期待値が決まるまで pending のままにします。期待値を書くことが、そのまま仕様の決定になります。実装との照合はまだしていません。このドキュメントは、仕様駆動開発で問題が見つかったことをきっかけに作り始めたもので、現時点で通らないテストがいくつかあります(どれかは未記録)。

## 改訂(2026-10-16): 本節が既存記述に優先する

2026-10-16 の会話で次の方針が確定しました。本節と矛盾する既存の記述(決定 #7、未決事項 #7・#19、トレードオフのタブ禁止の理由、想定問答 Q2・Q7、T02・T22・T36・T40・T41・T57・T63・T67 など)は、順次書き直します。書き直すまでは本節を優先してください。

1. **方針**: CommonMark 互換は目標にしない。`**` `*` などの Markdown 記法は、対応する標準プラグインの糖衣とし、`&strong(){}` などと等価とする。例外として、`:::` のフェンス付きブロックは既存記法(Qiita・rspress)との互換のために採用する。
2. **インデント**: 整形ルールとしてのみ扱う。ボックスの境界は `{{ }}` の対応で決まり、パーサーはインデントを使わない。リストの中の継続ブロックは、マーカーの幅に応じた内容の列に揃える(`- ` は2、`1. ` は3、`10. ` は4。参照実装で確認済み)。リストとの組み合わせは、コアの前処理で補う(`nested_blocks.rs` の現実装どおり)。
3. **タブ**: 禁止は整形ポリシーとして維持する。理由は閉じ位置の解釈ではなく、整形の一貫性とする。
4. **引数**: key=value を推奨形とし、1引数の省略形(`&bdi(ltr)`)は許可する。標準プラグインは、宣言された順番で位置引数を名前に対応づける。整形ツールは書かれた形を保つ。
5. **出力**: 標準プラグインは core が HTML に直接変換し、`<template>` を使わない。標準外プラグインは `<template class="umd-plugin umd-plugin-inline|block umd-plugin-[name]">` と `<data>` で出力し、content はエスケープしたテキストとする。再パースはホストの責務。
6. **標準外の既定表示**: ホストが処理しない場合、インラインは `<span class="umd-plugin umd-plugin-missing">content</span>` とする(T63)。ブロックはボックスのみ表示する(T64)。
7. **解釈の規則**: 名前が標準なら、パラメータが不正でも content は解釈する(T25)。名前が標準外なら、content は生テキストとしてホストに渡す(T57)。
8. **フェンス付きブロック**: `:::name 位置引数, key=value` の形で書き、閉じは行頭の `:::` のみとする。`@name(){{ }}` の糖衣であり、引数の文法は `@` 形式と同じ。名前の直後は空白とし、括弧形は許さない。入れ子は作らず、入れ子には `@` 形式を使う。内側の `:::` と閉じ忘れの扱いは、下の 10・11 を参照。
9. **標準プラグイン名の予約**: ホストは標準プラグイン名を上書きできない(提案。確認待ち)。
10. **閉じ忘れ**: 開始行(`@name(...){{` または `:::name ...`)がプラグインとして成立しない場合、開始行だけがテキストになる。中身は通常どおり評価され、中身のインラインプラグインは変換される。ブロック型とフェンス付きブロックで同じ規則とする(T15 を更新する)。
11. **フェンス付きブロックの入れ子**: フェンス付きブロックの中の `:::name` は処理せず、テキストとして扱う。閉じ記号は、開いているフェンス付きブロックを閉じる裸の `:::` のみとする。開いていない裸の `:::` もテキストとする。
12. **コードブロック**: プラグインより優先される記法であり、プラグインとしては定義しない。中身は一切変換しない(`:::` を含む、どの記法も変換されない)。

## 設計判断(ADR)

**状態**: 草案(調査中)

**決定の要旨**: 危険なものは文法の段階で禁止し、許可は名前付きのプラグインで明示的に増やす。

&#91;embedded content: 3層構造 · コアとホストの境界\]

コアはMarkdownを標準HTMLにするところまでを担当し、プラグインの処理はホストアプリとフロントエンドが担当します。

### 背景

- 目的は「セキュアで文法拡張可能なMarkdown」です。当初は「セマンティクス性を持ったMarkdown」でしたが、タグやBidi文字のような危険な文字をライブラリ側で禁止し、プラグインのホワイトリストで表現を拡張する発想に変わりました。
- 作者の説明では、MDXとは真逆の設計思想です。言い方の案として、拡張の目的は同じで、安全性の前提が逆(MDXは任意コードを書ける前提、umd-coreは既定で拒否)と整理できます。

### 決定

1. タグとBidi制御文字は、コアのレベルで禁止する。ただし、コードブロックの中は、コピペできることが求められるため、オプションで許可できる(既定は禁止。許可した場合のサニタイズはホストの責務。未決事項#24)。
2. 拡張はプラグインのホワイトリスト式にする。Bidiが必要な場合は標準プラグイン `&bdi(ltr){content};` で表現する。
3. 3層構造にする。umd-coreはMarkdownを標準的なHTMLにする処理だけを担当し、プラグインの解釈はホストアプリとフロントエンドが担当する。
4. 標準プラグインはコアに含める。色とサイズを除き、ほぼHTMLで表現できるものに限る。
5. 色は、ホストが明示的に制限を解除しない限り、カスタマイズ可能な色配列と対応するCSSで定めた色だけを使える。サイズは `xs` `sm` `lg` `xl` だけを選べる(これもカスタマイズ可能)。
6. 入れ子は最大5階層にする。上限はホストアプリが決める。上限を定めないと悪用する人が出るため。超えた場合は処理せず、エディタ上で警告する。カウントの責務は、標準プラグインとMarkdown標準の文法がコア、プラグインの入れ子がホスト。
7. インデントは整形ルールとして扱う(上の改訂 2・3 を参照)。ボックスの境界は {{ と }} で決まる。
8. コードブロックはプラグインより優先し、プラグインは最後に処理する。

### 保証の範囲(整理案・作者の確認待ち)

コアの出力(標準プラグインを含む)までを保証の範囲とし、ホストが制限を解除した範囲と、ホスト側プラグインの実装はホストの責任とする。

入れ子の上限(5階層)の保証は、1つのumdインスタンスの範囲に限る。ホストが内容を再パースして、5階層以上の入れ子を作る場合のチェックは、ホストが行う。

### リンクとメディア

リンク先URLとプラグイン自体の危険性の扱いは、ホストアプリの責務とする。リンクタグとメディアタグは、末尾に `{sha-...}` を書いてintegrityを指定できるよう、仕様を拡張している。

### エラーの扱い

不正な値(存在しない色など)と、引数の書式エラー(引用符なしの `bg=a=b` など)は、プラグインを処理せず、content だけを出力する。閉じ括弧のないプラグインは処理しない。診断(警告)を返すかどうかは未決事項#8。

この扱いは、コアが解釈する標準プラグインの場合です。コアが知らないプラグインは `<template>` が出力されてホストに渡されるので、エラー時にどうするかはホスト次第になります。

標準外のプラグインの引数の書式エラーは、コアはパースするが内容を保証せず、VS Codeのエディタ上で警告を出す。

## トレードオフと副作用

安全側に倒した設計の代償を、聞かれる前に言える形にしておくための一覧です。「得るもの」の列は、作者の発言にある理由と、私の整理が混ざっています。

| 判断                                                  | 得るもの                                                                                  | 代償                                                                                                                                                                             |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ブロックプラグインを `<template>` で出力する          | 中身が不活性なので、ホストが処理する前に描画・実行されない                                | ホストが処理しない環境では内容が見えない。アクセシビリティツリーや検索からも見えない(私の指摘)                                                                                   |

### 現時点で通らないテスト

実装との照合はまだ。通らないテストが分かり次第、IDと原因をここに記録する。性能・堅牢性のテスト(T19、T29、T65)は、実測が必要なので、先に確認する候補になる。

現在気づいているもの: プラグインと、`**` などのシンタックスシュガーの併用がうまくいかない。関連するテストは T24(`&color(blue){**blue**};`)と T25(`&color(reed){**red**};`)。具体的な症状と、再現の条件は未記録。併用のパターンを分けて確認するため、T74 と T75 を追加している。

### 意図的に先送りしていること

- **親のインスタンスから、子のインスタンスへ、文脈を渡す仕組み**(入れ子の深さ、見出しの連番、注釈の扱い)。現段階で設計するには負荷が大きいため、作者の判断で、いまは決めない。必要になったときに、使い方を見ながら決める(未決事項#9、#31、#32、T61、T99)
- **テンプレートの展開**(`{{ }}` の中の値の展開)。当分先のため、考えるのはあとにする(未決事項#21)

## ヒアリング想定問答

答えは、作者の発言にある事実だけで組み立てています。「要決定」を含む答えは、決めてから使ってください。

**Q1. 一言で言うと、何を作っていますか。** セキュアで文法拡張可能なMarkdownです。危険な文字はコアで禁止し、表現の拡張はプラグインのホワイトリストで増やします。当初は「セマンティクス性を持ったMarkdown」でしたが、この形に変わりました。

**Q2. MDXとの違いは何ですか。** 設計思想が真逆です。言い方の案は、拡張したいという目的は同じで、安全性の前提が逆、というものです。MDXは任意のコードを書ける前提で、umd-coreは既定で拒否し、許可したものだけを増やします。

**Q3. 描画後にサニタイズする方式では足りませんか。** 考え方は「存在しないものは『ないもの』とする」です。見た目上スペースを意味している文字なら、半角スペースか全角スペースで表現するべきで、制御文字は文法として存在させません。代替として、\<bdi> タグによる回避や、文法拡張(プラグイン)で表現できるため、問題ないと考えています。「ソースを見た人が見たものと、実際に処理されるものを一致させる」という言い方を足すこともできます(私の説明案)。ただし、コードブロックの中は例外で、現状はオプションで許可しています(未決事項#24)。具体例(Bidi制御文字など)を1つ用意しておくと伝わります。

**Q4. どこまでがセキュアだと言えますか。** 整理案では、コアの出力(標準プラグインを含む)までです。ホストが制限を解除した範囲と、ホスト側プラグインの実装は、ホストの責任になります。(未決事項#10)

**Q5. なぜ3層構造なのですか。** コアはMarkdownを標準的なHTMLにする処理だけを担当し、プラグインの解釈はホストアプリとフロントエンドが担当します。コアの責務が小さいので、保証の範囲を検証しやすくなります(説明案)。

**Q6. `<template>` で出力するのはなぜですか。代償はありますか。** 中身が不活性なので、ホストが処理する前に描画や実行がされません。代償として、ホストが処理しない環境では内容が見えず、スクリーンリーダーや検索からも見えません。安全性と引き換えにした性質として、先に言うのがよいです。

**Q7. 入れ子はどう扱いますか。** 最大5階層で、上限はホストが決めます。上限を定めないと悪用する人が出るため、上限を設けています。閉じ位置は {{ と }} の対応で決まり、インデントは整形ルールです。コードブロックはプラグインより優先します。5階層を超えたときの挙動は要決定です。(未決事項#2)

**Q8. なぜRustで書いているのですか。** 技術ではなく思想を前面に出した提案です。答えは、思想から導かれる設計判断で組み立てます。用意できる具体例は、先月、既存のパーサーにパッチを当てる方式では、入れ子のプラグインとシンタックスシュガーが動かないと分かったことです。

**Q9. 先月、土台を変えたそうですが、影響は。** 入れ子のプラグインとシンタックスシュガーが動かないという致命的な問題を、自分で見つけて方針を変えました。IPAのFAQでは、応募時点でプロトタイプが継続開発の段階にあることは必要ないと書かれています(Q2-3)。

**Q10. AIにコーディングを任せていると聞きますが、自分でプログラミングしていますか。** 全体の設計、入出力の仕様、テストケースの意図を自分で握っています。テスト結果だけでなく、テストケース自体が意図と合っているかを確認しています。分かりにくいロジックは必ず説明させています。FAQでは、提案者自らがプログラミングすることをPMが求めていて、最終的には提案内容とプログラム作成能力からPMが判断するとされています(Q1-7、Q4-1)。

**Q11. Rustは勉強しましたか。** 勉強はしていません、と事実のとおりに答えるのがよいです。そのうえで、分からないコードは説明させ、挙動で確かめていること、`unsafe` の場所や、WASMの境界でpanicしたときの挙動のように、コードを読まなくても確認できる点を確認していることを、具体的に答えられるようにしておくと安心です(確認項目は提案)。FAQのQ1-21は、不足している知識は明記し、勉強中であることを書く、と案内しています。

**Q12. 何を防いで、何を防がない設計ですか。** 防ぐのは、タグとBidi制御文字の混入、色とサイズの任意の値の注入(固定語彙で、出力はクラスだけなので複雑な処理が起きない)、インデントの解釈のずれ(タブ禁止)です。防がないのは、ホスト側プラグインの実装と、ホストが解除した制限です。リンク先のURLやプラグイン自体の危険性は、ホストアプリの責務です。リンクタグとメディアタグには、末尾に {sha-...} を書いてintegrityを指定できる仕様を拡張しています。
